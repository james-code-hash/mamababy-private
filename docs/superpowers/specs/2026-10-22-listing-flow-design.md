# 選品到上架與 SKU 綁定自動化 — 設計

日期：2026-10-22
狀態：草稿，待業主（James）核准
範圍：四個專案中的第 3 個（1 收單到出貨、2 清理多餘程式、3 本文件、4 備貨模式）

術語沿用 `CONTEXT.md`：候選商品、上架商品、SKU 綁定、完整成本、商品重量、內地運費、貨代費、蝦皮平台費、平台費情境。本文另用「商家 SKU」指 BigSeller 倉庫的 Merchant SKU；在 MamaBaby 的設定裡，它和蝦皮規格上的 `variationSku`（銷售 SKU）是同一個字串。

## 1. 為什麼要做

業主過去的上架方式：
- 人工在知蝦看趨勢，照抄別人的商品上架，再到 BigSeller 介面手動改內容，非常耗時。
- 定價靠感覺，沒精算，也沒有引流品、主打品這類策略。
- 圖片直接用 1688 原圖，上面有簡體字，台灣買家不喜歡。現有的 AI 做圖套固定的四張樣板（`modules/bigseller/product_image.py`），業主覺得「很死」。
- **最痛的是 SKU 綁定**：上架幾十個商品、幾百個 SKU 時沒有一次配好 1688 連結。之後每有新 SKU 被買，就要重新配一次。

業主的要求：**新 SKU 配不到貨源這件事不應該發生；上架完成，就必須已經綁好。**

店的定位：**母嬰＋寵物**。約 70% 商品走直購，30% 走台灣倉。備貨模式是專案 4，不在本範圍。

## 2. 目標

1. 從候選商品到蝦皮發佈，全程用 CLI 和排程完成，業主只做兩個決定：**勾選要上架的商品**、**審核後按發佈**。
2. **上架即綁定**：每個商家 SKU 在發佈前都已建好、已綁定 1688 規格，而且綁定方式和專案 1 採購時的查法一致、已驗證。任何一個 SKU 綁不上，該商品就不能發佈。
3. 既有商品補綁：截至 2026-10-22 的唯讀掃描結果如下。
   - 已上架商品 62 個、SKU 3,144 個。
   - 146 個 SKU 未綁定，分布在 17 個 1688 商品。
   - 36 個規格沒有填商家 SKU。
   - BigSeller 1688 商品池裡有 780 個規格沒有被用到。
4. 每天健檢貨源：1688 貨源消失時自動下架，並用 Slack 通知。
5. 定價精算、有策略：分兩種定價模式，每個規格各自算價，用真實重量，先賣原價、再開折扣。
6. 選品和審核都在網頁上做（清單比對版面），用手機也能操作。
7. 精修圖和影片：圖片去掉簡體字、有質感，每個商品各自企劃，母嬰和寵物各一套風格。

節奏：先試**每週上架 5 個商品**，順了再調整。

## 3. 非目標

- 備貨模式、台灣倉補貨（專案 4）。本專案只產出「適合備貨」的名單給專案 4。
- 訂單採購、貨代出貨（專案 1）。
- 清理舊程式（專案 2）。新流程不再使用的舊指令留給專案 2 移除；本專案只在新舊程式互相衝突時才處理。
- 自動改價：1688 漲價、實測重量變動時只提醒，不自動改。
- A/B 測試主圖。

## 4. 反目標（技術上能跑但算失敗）

- 有任何 SKU 未綁定的商品被發佈到蝦皮。
- 抓 1688 時被擋、逾時或回傳錯誤，卻被當成「貨源消失」而下架商品。**查不到不等於不存在。**
- 標示從未真正賣過的「原價」再打折，屬於虛偽原價，違反公平交易法。
- 精修圖出現簡體字、商品本身沒有的特徵，或捏造的認證。
- 把有法規風險的品項推薦上架：醫療器材（例如醫療口罩）、需 BSMI 的兒童玩具、需查驗登記的食品、需 BSMI 或 NCC 的電器、寵物食品與零食、動物用藥品。
- 未經業主同意就對正式 BigSeller、1688、蝦皮帳號做寫入或發佈。所有寫入指令預設 dry-run，加 `--commit` 才寫入。
- 修改專案 1 正在改的檔案（見第 11 節）。

## 5. 整體流程

```
[每週一 排程] 知蝦熱賣（母嬰 100632、寵物 100631）
   → 1688 尋源 → 定價試算 → AI 建議角色與法規標記
   → 選品頁（Firestore）── Slack：「本週候選已備好」
[業主] 勾選，可改角色 → 送出
[排程 worker] 對每個勾選的候選商品：
   1. 抓進 BigSeller 採集箱 → 認領成蝦皮草稿
   2. 改寫草稿：繁體標題與描述、類目屬性、規格、商家 SKU 命名、重量、出貨天數
   3. 建立商家 SKU → 加入 1688 商品池 → SKU 綁定 → 回查驗證
   4. 每個規格算價（目標成交價、原價）
   5. 精修圖組＋規格圖；主打品加做影片
   → 審核頁 ── Slack：「N 個商品待審」
[業主] 看圖、影片、價格、綁定對照 → 發佈／退回重做圖片／放棄（可直接改價）
[worker] 發佈到蝦皮，記下發佈日
[排程] 發佈滿 14 天 → 建立店內折扣活動，價格降回目標成交價 → Slack
[每天 排程] 貨源健檢 → 單一規格庫存設 0 或整個商品下架 → Slack
```

## 6. 第 1 期：上架即綁定（最先交付）

這一期沒有網頁。業主用 CLI 指定 1688 商品 ID，到 BigSeller 介面看草稿。

**第 1 期只建草稿，不發佈新商品**（業主決定）：草稿裡只有 1688 原圖，上面有簡體字，不讓它上線。發佈指令和第 15 天開折扣的排程在第 1 期就做好、測好，但發佈閘門要求圖片已經是審核過的精修圖，所以新商品要等第 3 期精修圖完成後才會第一次發佈。第 1 期真正上線運作的是既有商品補綁（6.4）和貨源健檢（6.5）。

### 6.1 由 1688 商品建立草稿

輸入：1688 offerId，可選商品角色（引流品或一般）。

1. **抓進採集箱**：`crawl_prices.link_crawl`，即 `POST /api/v1/product/crawl/linkCrawl.json`。之後用 `GET crawl/edit.json?id=` 取得規格、價格、庫存、重量（`crawl_prices.py:488-602`）。
2. **認領成蝦皮草稿**：目前沒有已知的 API。舊腳本用 Playwright 呼叫 Vue 元件 `crawl.selectImportShop` 和 `SelectStoreModal`（commit `2db8461`，店鋪 `shopee/<SHOP_ID>`）。**實作第一步要錄下這個 API**（見 6.6）。
3. **改寫草稿**：讀用 `GET /api/v1/product/listing/shopee/edit/{id}.json`，存用 `POST /api/v1/product/listing/shopee/draft/edit.json` 加 `operate:"edit"`。可寫欄位見 `product_edit.py:12-23`。要寫的內容：
   - 標題、描述：改寫成台灣用語的繁體電商文案，不捏造商品沒有的特性。
   - 類目必填屬性。
   - 規格名：照 1688 規格名轉成台灣繁體（OpenCC `s2twp`）。
   - 每個規格的 `variationSku`：`{offerId}-{繁體規格名}`，例如 `958331892364-粉色-L`。現有的 `bind-auto` 用前綴反查 offerId，專案 1 下單時用它反查，都依賴這個格式。**不得沿用 `update-from-1688` 的 `MABA{pid}-…` 命名。**
   - 商品重量、出貨天數：直購商品設為較長備貨，天數 = 1688 出貨時效 + 貨代時效，預設值放 config。
   - 各規格的原價（見第 8 節）。

### 6.2 建立商家 SKU 並綁定

1. **建立商家 SKU**：程式庫和歷史紀錄裡都沒有這個 API，以前都在 BigSeller 介面手動建（`reports/binding_scan_20260804.md:29`）。**實作要錄下這個 API**（見 6.6）。也可能存在「上架或認領時自動產生商家 SKU」的設定或接口，錄 API 時一併確認，並選最可靠的做法。
2. **加入 1688 商品池**：先 `addAli1688Product.json` 取得 `ali1688SkuList`，再呼叫 `saveAli1688Sku.json`。沿用 `sku_binding.auto_bind_offer` 的做法。
3. **SKU 綁定**：用 `saveOrUpdateRelation.json`，沿用 `sku_binding.bind_sku`。它會回讀確認，並刪除舊綁定。規格比對沿用 `match_1688_spec`，這次是由我們自己的命名反推，應該都是精確比對。
4. **供應商關聯**：用 `skuSupplierRelation/saveRelation.json` 寫入 supplierId 與採購 URL（`sync.link_supplier`）。專案 1 用 supplierId 查 `selectPlatformSkuPage`，缺了這步就下不了單。
5. **完成驗證（發佈閘門）**：對每個商家 SKU，用和專案 1 採購**相同的查法**（`orders.select_platform_sku` 的邏輯）確認剛好查到一筆 1688 對應。只要有一筆不符合，就不能發佈，並列出原因。本專案不得修改 `orders.py`，只能呼叫它的公開函式，或在自己的模組用同一支 API 查詢。

### 6.3 發佈

- 用 `draft/edit.json` 加 `operate:"editPublish"`。
- **發佈閘門**：發佈前一定要再跑一次 6.2 第 5 步的綁定驗證，並確認圖片已是審核過的精修圖。兩者有一項不符合就拒絕發佈。
- 發佈成功後，把發佈日、商品角色、各規格兩種價格寫進 Firestore，供 14 天後開折扣使用。
- 第 15 天開折扣的排程和發佈指令一起在第 1 期做好（設計者的決定），避免日後發佈的一般商品一直停在原價、比目標成交價高約 25%。

### 6.4 既有商品補綁

一個指令處理 3 號目標裡的 182 個 SKU：
- 146 個未綁定：以 `bind-auto` 為基礎，綁得上的自動綁。
- 36 個缺商家 SKU：依 `{offerId}-{繁體規格名}` 補上 `variationSku`、建立商家 SKU，再綁定。只有能從商品資料確定 offerId 時才補，否則列給業主。
- 綁不上的列清單，發到 Slack。
- 預設 dry-run。
- 780 個沒用到的商品池規格不處理，只在報告裡列出數量。

### 6.4b 規格挑選、起批量與庫存（設計者的決定）

- **哪些規格上架**：
  - 1688 已售完的規格不上架。
  - 超過蝦皮規格上限時（兩層規格、選項數和組合數都有上限，實際上限由實作者查證）不自動刪規格。指令列出所有規格，由業主用參數指定要保留哪些，例如 `--specs` 或規格檔。
  - 發佈閘門只檢查「要上架的規格」。
- **成本與起批量**：
  - 成本用買 1 件時的價格。有一件代發價就用一件代發價。
  - 起批量大於 1 的 1688 商品不能走直購（每張蝦皮訂單只買 1 件），建立草稿時拒絕，並建議改走備貨（專案 4）。
- **蝦皮庫存**：
  - 直購商品的蝦皮庫存照現有已上架商品的慣例設定。
  - 實作前要先確認 BigSeller 的庫存推送是否會把新商家 SKU 的倉庫庫存 0 推到蝦皮，把直購商品變成售完。如果會，要找出設定或處理方式，才能上線。

### 6.5 貨源健檢（每天）

- 檢查每個上架商品、每個 SKU 綁定的 1688 商品與規格目前的狀態。
- **資料來源**：1688 官方 API（`ali1688_api.py`）只能搜尋，查不到單一商品。可用的來源有三個，由實作者評估穩定度後選擇：
  - BigSeller `addAli1688Product.json`
  - curl 解析 1688 網頁（`sku_binding.parse_1688_page_data`，有 `offer.status`、每個 SKU 的 `canBookCount`）
  - 瀏覽器檢查（`product.check_1688_product_status`）
- **只有明確查到下架或規格不存在才動作**。被擋、逾時、解析失敗一律歸為「查不到」：不下架，連續數天查不到才發 Slack 提醒（天數放 config）。
- **單一規格消失或缺貨**：該規格庫存設成 0。蝦皮不能只下架單一規格，可參考 `sku_binding.zero_variations`。
- **整個 1688 商品下架，或全部規格都消失**：整個蝦皮商品下架（`batchOffline`）。
- 自動處理的紀錄寫進 Firestore，包括原本的庫存數字，供日後恢復時參考。
- **貨源恢復時不自動上架**，在 Slack 列出，由業主決定。
- **1688 漲價**導致目標成交價的毛利率跌破目標時，在 Slack 提醒，附上新的建議售價。不自動改價。
- 動作完成後統一發一則 Slack 摘要；沒有任何事發生就不發。

### 6.5b 上線方式：先試跑一週（業主決定）

貨源健檢與開折扣排程上線後，先跑 **1 週「只報告不動作」**：每天把「如果正式跑，會設 0 或下架哪些、會開哪些折扣」發到 Slack。業主確認沒有誤判後，才打開正式寫入（`--commit`）。正式寫入的開關放在 config 或排程設定，不寫死在程式裡。

### 6.6 錄 API（需業主事先同意）

開始寫第 1 期程式前，要在業主的 BigSeller 實際操作一次，錄下背後的 API：
- 從採集箱認領成蝦皮草稿。
- 建立商家 SKU。

這會在正式帳號建出測試草稿和測試 SKU，不會發佈。**動手前必須再問業主一次**，測完刪除。錄到的 API 和請求格式要寫進 `CLAUDE.md` 的 BigSeller API 參考段落。錄 API 用的探針腳本照規範用完即刪，不進版控。

## 7. 第 2 期：選品頁與審核頁

### 7.1 產生候選商品（每週一）

- **類目**：預設母嬰（`100632`）和寵物（`100631`），可用 `--cat` 指定。現在的程式寫死 `cat_id=100631`。
- **知蝦資料**：走 `route_tokens.route_request`。route token 過期時，不要整個失敗沒消息，要發 Slack 請業主重跑 `zhixia capture`。
- 修掉現有 pipeline（`modules/pipeline/zhixia_to_1688.py`）的問題：
  - 任一候選尋源失敗會 raise `SourcingBlocked`，導致整批不存檔。改成標記該候選失敗，其餘照常產出。
  - 結果列要保留 `offer_id`。
  - 知蝦輸出欄位和 pipeline 期望的欄位要對齊。
- **尋源**：用 `sourcing/search.py`，每個候選留 2 到 3 個 1688 貨源。
- 每個候選要準備的資料：
  - 蝦皮熱賣品圖、名稱、價格（作為競品價）。
  - 30 天銷量與成長率、類目排名、評分。
  - 1688 貨源縮圖與價格。
  - 兩種出貨方式的建議售價：直購和台灣倉。兩者差很多時標「適合備貨」（給專案 4）。
  - AI 建議：角色（引流品、主打品、利潤品、不建議）加一句理由。
  - 法規標記：第 4 節的品項一律標「不建議」，並寫明原因。
- 候選數量：每週約 20 到 30 個。

### 7.2 選品頁（業主選的 B 版：清單比對）

- 一列一個候選，由左到右：勾選框、蝦皮熱賣品圖、趨勢與 AI 建議、1688 貨源縮圖、定價試算（成本、運費、建議售價、毛利率、競品價）。
- 可切換類目、改角色、勾選。勾選時要選定用哪一個 1688 貨源，預設 AI 推薦的那個。
- 送出後寫入 Firestore，由 worker 接手。
- 尋源失敗的候選也要列出，標示原因。

### 7.3 審核頁

每個待審商品顯示：
- 精修圖組、規格圖、影片。
- 各規格的原價與目標成交價、毛利率。目標成交價可以直接改，改了就重算毛利率。
- 綁定對照表：繁體商家 SKU 對照簡體 1688 規格，附驗證結果。
- 重量是 1688 宣稱值或實測值。

可以做的動作：發佈、退回重做圖片（可附一句意見）、放棄。只有按發佈才會推到蝦皮。

### 7.4 架構（設計者的決定）

- **網頁**：Firebase Hosting 上的靜態網頁，用 Firebase Auth Google 登入。Firestore 安全規則只允許業主的帳號讀寫。
- **資料**：Firestore（專案 `mamababy-1bf68`，`(default)`，asia-east1）。
- **worker**：claw-arm-1 上的系統排程每隔幾分鐘查一次 Firestore 有沒有待處理的勾選或審核動作，有就處理。不經過 AI。
- **通知**：Slack。共用專案 1 的 `modules/notify/slack.py`，不另外寫一套。
- **Firestore 連線**：共用專案 1 的 client，不另外寫一套（見第 11 節）。

## 8. 定價

- **全專案唯一公式**仍是 `modules/profit.py` 的 `estimate_profit`，在它上面加策略層，不另外寫公式。
- 每個商品有角色，在選品頁由 AI 建議、業主可改：
  - **引流品**：目標成交價 = 不虧錢的最低價，用平日費率 20%、退貨率 5% 計算。**不標原價、不開折扣。**
  - **一般商品**（主打品、利潤品）：目標成交價 = 毛利率 30% 的價格，用平日平台費情境計算。毛利率**沒有硬門檻**，低於目標只標黃提醒。
- **原價** = 目標成交價 ÷ 0.8，再取心理價位尾數。「0.8」放 config。
- **心理價位尾數**（業主同意）：無條件進位到尾數 9 的價格，例如 118 → 119、241 → 249。精確規則由實作者決定，寫在 config 或程式說明裡。
- **每個規格各自算價**：成本、重量依規格不同。
- **出貨方式**：本專案上架的商品預設直購，用直購運費計算（現在是每公斤 ¥12）；台灣倉運費是每公斤 ¥3。兩種價格都算出來顯示。
- **重量**：
  - 上架時用 1688 宣稱值。
  - 之後改用貨代實測重量的平均。實測資料由專案 1 寫入 Firestore（見第 11 節）。
  - 實測值和宣稱值差 20% 以上（門檻放 config）時，在 Slack 提醒並附上重算的建議售價，不自動改價。
  - 拿不到宣稱重量時標「重量未知」，審核頁提醒業主確認。不得默默套用 0.25 公斤之類的假設值。
- **先原價、再折扣**（業主同意）：
  - 一般商品發佈後用原價賣 14 天，讓原價成為真實賣過的價格。
  - 第 15 天由排程用 BigSeller 店內折扣活動 API（`promotions.py`，`DISCOUNT_ADD`）把價格降到目標成交價，並發 Slack。
  - 折扣活動有期限的話，到期前要自動續期或發 Slack 提醒。
- **設定統一**：`config.TARGET_MARGIN_RATE` 改為 0.30，拿掉「硬門檻」註解。`pricing` 指令預設改讀 config，不再自帶 0.35。`reprice-all` 依賴寫死的 `reports/price_audit_20260822.json`，本專案不修，留給專案 2。

## 9. 第 3 期：精修圖與影片

### 9.1 圖組（依買家決策順序，每張只負責一件事）

1. **主圖**：搶點擊。商品清楚、背景乾淨，縮成手機小圖也認得出。最多一個小標籤。
2. **痛點或情境**：母嬰是媽媽和寶寶的使用場景，寵物是毛孩和主人的互動。
3. 到 5. **賣點**：一張一個賣點，用畫面證明，例如材質特寫、尺寸對比。
6. **尺寸規格表**。
7. **規格總覽**：多色、多尺寸一張看完。
8. **細節特寫**。

另外，**每個規格各一張規格圖**（蝦皮的 option image）。

依角色調整張數：
- 主打品：完整 8 張＋規格圖＋影片。
- 引流品：主圖、2 張賣點、規格圖，不做影片。
- 利潤品：張數由實作者決定。

### 9.2 每個商品各自做美術企劃

- 先分析知蝦上同品項前 10 名競品的主圖，刻意做出差異。
- 賣點只從 1688 的圖片、規格和描述裡取，不編造。
- 生成工具：claw-arm-1 上已登入的 Codex（`codex exec`，沿用 `product_image.generate_with_codex` 的呼叫方式）。拿掉現在的固定四張樣板。
- **風格**：
  - 母嬰：溫暖、柔和、乾淨，強調安全感。
  - 寵物：明亮、活潑，用「毛孩」這類用語。
  - 兩類共用品牌色、字體、角落小標誌，讓買家認得出同一家店。
- 文字一律台灣繁體、台灣用語，避免大陸電商的大紅字和「爆款」風格。
- **生成後自動檢查**：用視覺模型檢查有沒有簡體字、商品外觀是否和 1688 原圖一致。沒通過就重做，重做次數有上限，超過就在審核頁標示。
- **圖片託管**：改存 Firebase Storage，取代 `product_image.host_image` 的 Telegram 圖床。BigSeller 收到圖片網址後會轉存到蝦皮 CDN。
- 審核頁按「退回重做」時，把業主的意見帶進下一次的企劃。

### 9.3 影片（只做主打品）

- 15 到 30 秒，直式或方形，前 3 秒就要讓人看懂商品是什麼。蝦皮在手機上靜音自動播放，所以靠畫面和繁體字幕說話，不靠配音。
- 用審核過的精修圖生成 2 到 3 段動態鏡頭，再接起來，加上字幕和店家標誌。
- 1688 原影片預設不用，只當參考素材。
- 現在的影片生成（`modules/gemini/video_gen.py`、`flow_video.py`）是在瀏覽器裡操作，雲端跑起來脆弱。實作者要評估改用 API 生成，評估結果寫進計畫。
- 上傳沿用 `video_upload.upload_and_bind_video`，純 API，已驗證可用。
