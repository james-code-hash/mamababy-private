# 收單到出貨自動化 設計

日期：2026-10-22
範圍：直購模式下，從蝦皮缺貨訂單 → 1688 採購 → 通知貨憨憨出貨的整段自動化。四個專案中的第一個（順序：收單到出貨 → 清理程式 → 補上架 → 備貨模式）。

詞彙以 [CONTEXT.md](../../../CONTEXT.md) 為準；相關 ADR：0004（付款前覆蓋）、0006/0007（阻塞）、0010（BigSeller 為庫存真相）、0011（不拆單）、0012（訂單驅動採購）。

## 為什麼做

過去每一步都靠人工：有訂單時找 1688 對應商品、建採購單、隔天到貨代網站通知寄出，非常耗人力。程式碼雖然有 `orders prepare-purchase`、`bs purchase sync`、`orders fulfill-shipping` 與兩支 cron 腳本，但：

- 排程原本跑在 claw-arm-1，由 Hermes（AI agent）管理，**Hermes 已移除，目前沒有任何排程在跑**。
- 新訂單 cron 有計數 bug（dry-run 永遠輸出「建立 0 / 覆蓋 0」，`has_actionable_batches` 永遠回 False），實際上從未動作。
- 其他缺陷見下方「必修缺陷」。

## 目標

業主（James）**唯一固定要做的事是在 1688 付款**。其餘全自動：

1. 每 2 小時收集缺貨的蝦皮訂單（直購），按供應商合併，在 1688 下單到「待付款」，發 Slack 通知付款。
2. 未付款期間若同供應商有新訂單，取消舊的待付款單，合併重建一張，再通知付款。付款後才定案。
3. 付款後：自動推進採購單狀態；每張蝦皮訂單所涉及的**所有**供應商運單號到齊後，自動通知貨憨憨出貨，並逐項標明對應的 1688 運單號。
4. 出狀況時發 Slack，人工處理後用既有指令結案。

成功標準：連續一週真實訂單，除付款與 Slack 通知的例外外，不需任何人工操作；沒有買錯、漏買、重複付款、錯送運單號。

## 非目標

- 上架時就完成 SKU↔1688 綁定（屬第 3 個專案「補上架」）。本專案只做防護。
- 備貨模式（先買放台灣倉）。本專案只處理直購；BigSeller 已從庫存分配的訂單不是缺貨訂單，自然不會被採購（現行行為，保留）。
- 自動付款。
- 自動提交貨憨憨退貨申請（本次只通知；之後若找到 API 再說）。
- 大規模清理程式（第 2 個專案）。本專案只刪改自己碰到的程式。

## 反目標（做了也算失敗）

- 同一批貨付兩次款（舊單沒取消成功、又建了新單）。
- 一張蝦皮訂單只買了部分商品（違反 ADR 0011）。
- 只送部分運單號給貨代，貨代就出貨。
- API 出錯被當成「0 筆」，看起來一切正常（靜默失敗）。

## 流程

### 排程

- 跑在 **claw-arm-1**（雲端機器，常駐）。用系統排程（cron 或 systemd timer，由實作者選）直接跑 Python，不經任何 AI agent。
- **每 2 小時一次**，一次跑完整個循環（見下）。實作者可決定「付款後那半段」是否更頻繁跑，只要不影響採購半段的 2 小時節奏。
- AI（Claude）不在排程裡；業主收到 Slack 後，有需要再開 Claude 處理。

### 一次循環（建議單一進入點，例如 `orders cycle [--commit]`）

1. **推進已付款採購**：沿用 `advance_purchase_pipeline`（刷新 1688 物流 → 草稿/待發貨/在途中推進）。
2. **偵測取消**：對照蝦皮訂單狀態，處理三種取消時間點（見「例外處理」）。
3. **通知貨代**：對「所有相關採購都已有運單號」的蝦皮訂單，呼叫貨憨憨 place-order，逐項帶上該項自己的 1688 運單號。
4. **採購**：讀缺貨訂單 → 按（供應商, 收貨倉）合併 → 決定每家要「新建 / 覆蓋未付款單 / 不動」→ 在 1688 下單到待付款。
5. **Slack 摘要**：有需要付款的單、有例外、或有錯誤時才發；什麼都沒發生則靜默。

### 採購批次規則

- 批次鍵：（供應商, 收貨倉）。收貨倉預設貨憨憨倉（設定 `PURCHASE_WAREHOUSE_ID`）。
- 某供應商：
  - 沒有現行待付款單 → 新建並在 1688 下單。
  - 有**已下單但未付款**的單，且這次的訂單集合與它不同（新增或減少） → **先取消舊的 1688 待付款單並刪除 BigSeller 採購單，確認取消成功後**，才用完整訂單集合重建並下單。取消失敗 → 不建新單、發 Slack 告警（避免重複付款）。
  - 訂單集合相同 → 不動（沿用指紋去重，ADR 0004）。
  - 舊單**已付款** → 舊單定案不動；新訂單另開一批。
- **只管自己建的單**（設計者決定）：自動化建立的採購單要帶可辨識的標記（例如 note 格式或 Firebase 紀錄），取消、刪除、覆蓋只作用在有標記的單上。業主手動建立的採購單一律不動。上線切換時現存的未付款單/草稿不覆蓋，第一輪列在 Slack 讓業主自行處理。
- 這是對 ADR 0004 的擴充：現行程式把「已在 1688 下單（有 `aliOrderNo`）」就當成鎖定；新規則改為「已付款」才鎖定。需更新 ADR 0004 或新增 ADR 記錄此變更。

### 付款通知（Slack）

每次有新建或重建的待付款單，發一則訊息，列出每家供應商：供應商名稱、1688 訂單號、金額、包含哪些蝦皮訂單；若是重建，註明取代了哪張舊單（舊單已取消）。業主只要照最新一則付款即可。

### 通知貨代

- 一張蝦皮訂單可能向多家供應商採購。**每一家的運單號都到齊**才送貨憨憨；送出時每個商品項帶它所屬採購單的運單號。
- 現行 `build_purchase_order_mapping` 以蝦皮訂單號為鍵、後寫覆蓋前寫（orders.py:473），`huohanhan/client.place_order` 把同一個運單號套到所有商品項（client.py:218-235）。兩者都要改成「一張蝦皮訂單 → 多張採購單」。
- **分包**：1688 店家可能把一張採購單拆成多包、各有運單號（業主確認：會發生但機率不高；貨憨憨接受同一張蝦皮訂單不同商品帶不同運單號）。一張採購單要能有多個運單號。能從 BigSeller 資料對出「哪個商品在哪一包」就照實送；對不出來（例如同一商品數量分在兩包、資料沒有逐項對應）就不送貨代，Slack 通知業主手動處理（設計者決定，因發生率低）。「運單號到齊」的判斷要考慮分包。
- **通知去重**（設計者決定）：同一件事（同一張待付款單、同一個下單失敗原因、同一個阻塞）只在第一次發生或狀態改變時通知，不每 2 小時重發；未付款單每天提醒一次。
- 送出後沿用現行驗證（訂單離開貨代待處理清單）與 `forwarder_submission` 紀錄。
- 已付款但遲遲沒有運單號、或已有運單號但貨憨憨待處理清單裡找不到這張訂單：超過合理時間後發 Slack 提醒（門檻由實作者訂，需寫在設定裡）。

## 例外處理

| 情況 | 程式做什麼 | 人做什麼 |
|---|---|---|
| 商品 SKU 配不到 1688 貨源 | 整張蝦皮訂單不採購（不拆單），Slack 列出訂單與 SKU | 綁好後下一輪自動採購。理論上不該發生，應在上架時解決（第 3 專案） |
| 一個 SKU 綁多個規格挑不出來 | 同上（PR #10 已實作整單跳過，改成 Slack 通知） | 清理綁定 |
| 付款**前**客人取消 | 下一輪重建時自動移除該訂單（若該供應商只剩這張，取消整張待付款單） | 無 |
| 付款**後**、1688 未出貨前取消 | 只有當這張 1688 單內**所有**蝦皮訂單都已取消，且 API 能取消/申請退款時才自動做並通知（設計者決定：避免連帶取消其他客人的貨）。其餘情況（含只取消其中一部分）標記阻塞，Slack 告知要去 1688 處理哪一張、哪些商品 | 必要時到 1688 網頁申請取消或部分退款 |
| 1688 下單失敗（下架、缺貨、起批量不足、規格或價格變動等） | 該批次本輪不下單，Slack 通知原因與受影響的蝦皮訂單；下一輪照常重試 | 業主決定：一律通知業主，由業主處理（例如請客人取消、改綁貨源）。系統不自行剔除訂單 |
| 業主放著不付款，1688 待付款單被自動關閉 | 該訂單仍是缺貨訂單，下一輪重新下單並通知 | 業主決定：通知業主。不想買就請客人取消蝦皮訂單，系統下一輪自然不再採購 |
| 1688 **已出貨**後取消 | 標記阻塞、不送貨代，Slack 告知蝦皮訂單號、1688 訂單號、運單號 | 與店家談退貨 → 貨憨憨提交退貨申請（上門退貨）→ `orders resolve-block` 結案 |
| **已通知貨憨憨**後才取消 | 不再對這張訂單做任何貨代動作；Firebase 記錄「已寄出後取消，貨轉為台灣倉庫存」，Slack 通知 | 業主確認：貨憨憨無法攔截，貨會寄到台灣倉存放成庫存、可再銷售，但會再收一次包裝費。無需處理，供日後備貨模式與收益報表參考 |
| 任何 API 錯誤、登入失效 | 本輪中止受影響的步驟、非零結束、Slack 告警。**不得把錯誤當成空結果** | 視告警處理，必要時叫 Claude |

阻塞記錄與結案沿用 `orders list-blocked` / `orders resolve-block`。

## 必修缺陷（盤點時發現，均在本範圍內）

1. `prepare_purchase` dry-run 不累計計數，導致 cron 永遠判斷「無事可做」（prepare_purchase.py:196-199、cron_new_order_alert.py:51-56）。
2. 採購↔蝦皮訂單映射後寫覆蓋前寫（orders.py:473-474），多供應商訂單只送一個運單號（huohanhan/client.py:218-235）。
3. 訂單有一項配不到供應商時，其他項照買（只有「多重綁定」會整單跳過，prepare_purchase.py:158-159），違反 ADR 0011。
4. API 錯誤靜默回空：`get_out_of_stock_orders`（orders.py:441-442）及同類函式。
5. 取消狀態拼字不一致：`"cancelled"`（blocked_handling.py:56）vs `"canceled"`（orders.py:674），其一可能永遠比不到；且只偵測送貨代前的取消。
6. 偵測取消在 dry-run 也會寫入阻塞紀錄（fulfill_shipping.py:51）。
7. cron 以比對 CLI 輸出文字判斷結果（`_NO_SHIPMENT_MARKERS` 等），脆弱。新進入點應直接呼叫編排函式取得結構化結果。
8. 通知改 Slack：移除排程路徑上的 Telegram（`cron_utils.send_telegram`）。其他用途的 Telegram（如 `image-optimize` 用 Telegram 當圖床）不在本範圍。
9. `deploy-linux.md` 描述與實際不符（說 cron 建立的草稿已有 1688 訂單號），且路徑寫死 Hermes 目錄 `/home/openclaw/.hermes/profiles/ecommerce/...`（cron_utils.py:25-28）。改成不依賴 Hermes 的設定。

## 待查證的外部能力（實作第一步先查，結果決定做法）

1. **付款狀態**：如何判斷一張 1688 訂單已付款。候選：BigSeller 採購單欄位（`platformOrderStatus` 等，值域未知）；1688 官方 API 訂單詳情（`ALI_1688_AK`，目前只確認有商品搜尋權限）。
   - 若兩者都不行：**不得**猜測。停下來回報業主，可能需要改流程（例如請業主付款後在 Slack 回報）。
2. **取消未付款的 1688 訂單**：BigSeller 是否有 API；或 1688 官方 API 的取消交易能力。
   - 若都沒有：「覆蓋未付款單」無法安全實作（會重複付款）。停下來回報業主，可能請業主在 BigSeller 後台手動取消一次，錄下實際呼叫的 API。
   - 1688 未付款單是否會自動關閉、多久關閉，一併查明，寫進文件。
3. **已付款訂單申請取消/退款**：BigSeller 或 1688 API 是否支援。沒有就走人工（見例外處理），不阻擋本專案。
4. **貨憨憨退貨申請 API**：只查、記錄結果，本次不實作。

查證只能用唯讀呼叫或業主提供的操作錄製；不得為了測試而在正式帳號取消或建立真實訂單，除非業主明確同意。

## 儲存：改用 Firebase

業主決定：**所有需要儲存的資料都寫到 Firebase**，未來自己的收益報表也要從 Firebase 抓。

- 目標：Firebase 專案 `mamababy-1bf68`（MamaBaby）的 Firestore `(default)` 資料庫（Native 模式、asia-east1、免費層）。2026-10-22 查詢時尚無任何 collection。
- 取代本地 SQLite（`config.ORDER_PROCESSING_DB` = `data/order_processing.db`，ADR 0001）。需新增 ADR 記錄此變更，並更新 ADR 0001 為已取代。
- 現有三個 store（`FingerprintStore`、`ForwarderSubmissionStore`、`BlockedOrderStore`）改為 Firebase 實作，維持現有 store 介面讓編排層與測試不必大改；測試繼續用假 store / 記憶體實作，不打 Firebase。
- BigSeller 仍是庫存與訂單分配的真相（ADR 0010 不變）。Firebase 存的是：工作流狀態（指紋、貨代提交、阻塞），以及本流程經手、之後收益報表需要的事實。
- **為收益報表預留的事實**（本專案只負責寫入，不做報表）：每張採購單的供應商、1688 訂單號、商品明細與金額、運費、付款時間（若查得到）、對應的蝦皮訂單號；每次通知貨代的時間與運單號。蝦皮營收、平台費用、貨代費用等不在本流程經手的資料，留待報表專案決定來源。
- 憑證：claw-arm-1 用 service account 金鑰，路徑放 `.env`，金鑰檔不進版控。
- 若要搬移 claw-arm-1 上舊 SQLite 的資料：先看資料量，量小可不搬（狀態可從 BigSeller 重新推導），由實作者判斷並說明。
